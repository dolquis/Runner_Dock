# 02. 要件定義

**区分:** 規範 / **版:** MVP v0.1候補 / **優先度:** P0=公開MVP必須、P1=次段階、P2=将来

## 1. 対応範囲

MVPは1台のWindows 11 x64 PC、1つの承認済みprivate repo、Windows Runner 1件とWSL Ubuntu Runner 1件を最低受入構成とします。データモデルは複数repo・Organizationに拡張可能としますが、対応済み表示は実装・テスト後です。

GitHub.comが対象です。GHES、Windows ARM64、macOS、Linux単独ホスト、Docker Backendは初期保証外です。WSL1は検出してWSL2への案内を行い、その場で無断変換しません。

## 2. 機能要件

| ID | 優先 | 要件 | 受入条件 |
|---|---|---|---|
| FR-001 | P0 | 環境診断 | OS/arch/WSL版/ディストリビューション/空き容量/接続/権限を区別し、結果と対処を表示する |
| FR-002 | P0 | GitHub認証 | App Device Flowで認証・失効・refreshを扱う。PAT補助経路も権限と期限を表示する |
| FR-003 | P0 | セットアップ計画 | 実行前にダウンロード、保存先、追加ユーザー、登録先、必要権限、再起動の有無を一覧化する |
| FR-004 | P0 | Windows Runner作成 | 公式配布物検証→登録→起動→GitHub照会を行い、失敗段階を記録する |
| FR-005 | P0 | WSL Runner作成 | 指定したWSL2 Ubuntuに非root Runnerを作成し、Windows側から寿命を管理できる |
| FR-006 | P0 | 一括起動 | 設定後は通常権限の1操作で対象Runnerを起動する。片側失敗は部分成功として表示する |
| FR-007 | P0 | 停止の安全性 | Busy・Unknown時は既定で停止を保留し、強制停止は対象と影響を再確認する |
| FR-008 | P0 | 二重ヘルス監視 | Local/GitHub/観測時刻/鮮度/理由を分離表示する。API障害をoffline扱いしない |
| FR-009 | P0 | GUIとAgentの独立 | GUIを閉じてもAgentが継続し、再起動したGUIが二重Agentを作らず再接続する |
| FR-010 | P0 | ログ・診断 | Runner/Agent別のログ、検索、秘匿化した診断書き出し、保存上限がある |
| FR-011 | P0 | 事前選択Workflow生成 | Windows/Linuxの最小テンプレート、必要Secret、注意点、差分プレビューを出力する |
| FR-012 | P0 | 信頼・課金方針 | ローカル対象イベント/refとhosted利用同意を必須にし、未信頼イベントはローカル候補にしない |
| FR-013 | P0 | 再試行・回復 | 再クリック・再起動・一部失敗でもRunnerを重複登録しない。状態再照合を行う |
| FR-014 | P0 | 更新と版管理 | 本体/Guest/公式Runnerの版を別表示し、Busy中の破壊的更新を避ける |
| FR-015 | P0 | 対象限定の削除 | 製品が管理するRunner/ファイルのみ削除し、登録解除失敗・保留を表示する |
| FR-016 | P0 | リソース可視化 | PC全体と取得可能なRunner/WSL指標を区別し、採取不能はUnknownとする |
| FR-017 | P0 | CLI最小操作 | `doctor`、`status`、`node start`、`node stop`をAgent経由で提供する |
| FR-018 | P1 | 複数scope管理 | repoとorgで資格情報・権限・Runner IDを混同せず管理する |
| FR-019 | P1 | Workflowパッチ適用 | 対応可能な構文だけをCST/ASTで編集し、原本ハッシュの一致後に適用する |
| FR-020 | P1 | 既存Runner取込 | 登録・サービス・管理主体を読取診断し、明示的な移管後だけ操作する |
| FR-021 | P1 | 高度な資源制約 | Job Object/cgroup等を検証した範囲で適用。WSL全体設定との違いを表示する |
| FR-022 | P2 | 一時環境・Docker | 使い捨て実行環境とログ保全。Runner解除だけで隔離を主張しない |

FR-011のMVPは**生成・保存まで**です。既存Workflowを自動書換えする機能はFR-019であり、未対応構文に対して推測で変更しません。

## 3. 非機能要件

以下の値は設計上の測定目標です。検証前の性能保証ではありません。

| ID | 要件・目標 | 測定・判断方法 |
|---|---|---|
| NFR-001 | 日常操作で昇格しない | 起動・停止・監視でUACが発生しない。OS導入操作は除く |
| NFR-002 | UI応答を維持 | ダミー負荷下の操作受付p95 300ms以内を初期目標とし、処理完了とは分ける |
| NFR-003 | 再現可能なビルド | exact toolchain、lockfiles、依存監査結果をリリースに対応付ける |
| NFR-004 | 秘密を永続平文保存しない | DB/ログ/設定/診断/フロントストアの検査を行う |
| NFR-005 | 外部公開ポートを必須にしない | ローカルIPCとアウトバウンドHTTPSで主要機能が動く |
| NFR-006 | バックプレッシャー | IPC frame 1MiB以下、ログ購読キューの上限、ドロップ件数表示 |
| NFR-007 | 状態鮮度が可視 | Local既定3秒、GitHub既定30秒を目安に最終成功時刻を表示する |
| NFR-008 | 停止・取消の追跡 | operation IDで受付/進行/結果/部分失敗を確認できる |
| NFR-009 | アクセシビリティ | 色だけに頼らずラベル・アイコン・キーボード操作・拡大表示に対応 |
| NFR-010 | 破壊変更が明示的 | WSL削除、強制停止、秘密更新、Workflow書込は確認と監査履歴を残す |
| NFR-011 | 状態永続化の一貫性 | AgentだけがDBを書込み、PIDだけで再接続先を決めない |
| NFR-012 | 外部依存障害への耐性 | 401/403/404/429/5xx・タイムアウトを分けて上限付き再試行する |

## 4. 最低限のユーザーストーリー

**US-01 構築:** 利用者は変更計画を確認してWindows/Linux Runnerを作る。WSLの導入に再起動が必要なら作業が保存され、復帰後に再開できる。

**US-02 起動:** 利用者はNode起動を押す。Windowsだけonlineになった場合、Ubuntuまで成功したと表示されず、Ubuntuの再試行だけができる。

**US-03 停止:** Linuxビルド中に停止を押すと停止待ちになる。強制停止にはジョブ中断の警告が必要で、既存の別WSLディストリビューションは停止しない。

**US-04 代替実行:** 利用者がhosted実行を許可したテンプレートでは、事前照会時に自宅Runnerが利用不能ならhostedを選ぶ。判断後の障害は別の復旧問題として扱う。[S01](19_SOURCES.md#s01)

**US-05 トラブル:** トークン失効時にRunnerプロセス自体が動作していても、管理画面は「監視認証が失効」と示す。自動的な再登録や削除をしない。

## 5. リリースを止める条件

他人のPRが既定経路で私用Runnerに到達する、Busy中に無確認で停止する、秘密をログへ書く、既存WSLを巻き込んで停止する、APIエラーを成功扱いする、UIを閉じるとRunnerが予期せず落ちる。このいずれかが未解決なら公開MVPは出しません。
